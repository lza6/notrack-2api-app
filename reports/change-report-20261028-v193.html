DuckFlow 2API 变更报告 — v1.9.3 审计轮（2026-10-28）

上下文：为什么做这次变更

上一轮把 known-issues 清零后，用户再次下发全量审计令。这次审计的起点不是"还缺什么功能"，而是"上一轮声称的一切，哪些其实没有证据"。核实结果是：执行骨架（policy / workflow_status / test_ledger / evidence）、CHANGELOG、AGENTS、5 个技能与 5 个记忆文件全部不存在——即"审计闭环"本身只有结论、没有账本。同时本轮真实验证抓出两个 P1。

直觉：关键判断与取舍

  • "200 就是成功"是错的。接口矩阵跑通时发现非流式对话偶尔返回 200 + content:""。这在监控上看是 100% 健康，在用户侧是"AI 不说话"。修复不是补日志，而是把这种结果变成可重试的 502。
  • 自愈写了不等于接上了。fe-version 自愈上一轮有 6 个单测、面板也透出了状态，但真实 418 发生时 source 恒为 builtin——因为触发点接在一条运行时根本不会走的函数上。教训：断言"功能生效"必须看运行时状态字段，不能看单测绿。
  • 正则要对着真实页面写。首页实际只有 serp_20261027_210303_ET（无 hash 后缀），旧正则要求 20+ 字符所以永不匹配；同时加"防降级"规则，避免用首页裸 token 覆盖已验证的带 hash 工作值。
  • 不夸大自愈的作用。实测新旧版本串各自都有 418，说明 418 主因是挑战层而非版本漂移。因此结论只写"基础设施 + 可观测性"，不写"解决 418"。

Q5（简答）：本次审计发现"上一轮声称的闭环"缺了什么？这说明审计流程该补哪一环？

答案： Q1=C（completion_is_empty() 判定后返回 502，让客户端重试，而不是静默给空串）。 Q2=错（上一轮正因触发点接在运行时不会走的函数上，单测全绿但运行时 source 恒为 builtin；必须看运行时状态字段）。 Q3=因为带 hash 的形态已被验证可用，裸 token 是它的前缀、属"更弱/未验证"形态；无条件覆盖会降级。故规则为"互为前缀时保留更长者"。 Q4=C（X-Panel-Token 头；query token 会经浏览器历史、Referer、代理日志泄漏）。 Q5=缺执行骨架与证据台账（policy/workflow_status/test_ledger/evidence、CHANGELOG、AGENTS、技能与记忆文件）。说明"审计"必须产出可回溯的账本，而不是只有结论；本轮已补齐，并把"每个通过都要有原始命令输出"写进 policy 门禁。
